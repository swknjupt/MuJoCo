## 0. 一句话产品定义

> **在机器人策略或控制器上真机之前，让它在真实控制时序、真实总线、真实执行器限制和可控故障下反复测试；每次失败都能复现、定位和追溯。**

更通俗地说：

> 给机器人团队做一个“真机前的飞行模拟器 + 压力测试场 + 黑匣子”。

平台不是让策略更聪明，而是让策略团队更早、更安全、更可重复地发现：

- 策略会不会在真实时序下失效；
- 推理超时后系统会怎样；
- 编码器丢帧、通信延迟和力矩衰减会不会导致失控；
- 模型和真机到底差在哪里；
- governor 能不能在策略跑飞时兜住；
- 修完问题后有没有引入新回归。

## 1. 产品定位

### 1.1 首批目标客户

优先服务具身智能机器人研发团队，包括：

- 人形机器人团队；
- 四足机器人团队；
- 机械臂和移动操作团队；
- 使用 RL、模仿学习或端到端策略的机器人公司；
- 需要验证自研控制器与关节执行器的团队。

典型客户角色：

| 角色 | 关心的问题 |
|---|---|
| 技术负责人 | 是否能把策略安全、可重复地推进到真机 |
| 控制工程师 | 仿真和真机的差异在哪里，怎么定位 |
| 测试工程师 | 如何批量运行故障场景并自动报告 |
| 安全负责人 | 策略失效时有没有独立兜底和证据 |
| 产品负责人 | 真机测试成本、进度和质量风险能否下降 |

### 1.2 产品形态

早期产品形态：

> **软件工具链 + 实时目标机。**

软件负责：

- 模型和策略导入；
- 实时模型编译；
- 场景与故障配置；
- 测试编排、回放和报告；
- 模型误差与仿真/真机对比。

实时目标机负责：

- 1kHz/2kHz 控制；
- 真实总线与 I/O；
- 推理超时和 governor；
- 执行器 HIL；
- 可选 FPGA 高确定性 I/O 与执行器仿真。

FPGA 是实时盒子内部的能力模块，不是首版产品的独立卖点，也不是通用 MuJoCo 物理加速器。

### 1.3 产品边界

平台明确不承诺：

- 让策略绝对安全；
- 用仿真覆盖替代最终真机认证；
- 用测试覆盖率证明系统安全；
- 在 FPGA 上运行完整、通用的 MuJoCo；
- 台架化所有灵巧操作和接触任务；
- 替代客户的训练管线。

平台承诺的是：

- 提前暴露可测试的问题；
- 让失败可复现；
- 让模型误差有量化和适用范围；
- 让策略失效时有不依赖策略的安全路径；
- 让每次测试留下完整证据。

## 2. 产品卖点

### 2.1 “仿真里过了，上真机前再考一次”

**客户问题**

客户常见流程是：

```text
MuJoCo/Isaac 中训练通过
→ 直接上真机
→ 偶发失败
→ 无法判断是模型、策略、时序还是硬件
```

**产品能力**

把同一个策略放入真实或近似真实的控制链路：

- 真实 1kHz 控制周期；
- 真实推理耗时与超时策略；
- 真实总线延迟；
- 真实编码器噪声和丢帧；
- 真实电机限流与执行器约束；
- 可控故障注入。

**客户价值**

在昂贵的真机联调前，先发现那些只在真实时序和真实接口下才出现的问题。

### 2.2 “同一个偶发故障，可以重复十次”

**客户问题**

机器人现场和实验室里最常见的失败是：

- 昨天出现过，今天复现不了；
- 录像有，但日志不完整；
- 同一个策略有时正常、有时抖动；
- 客户现场失败无法带回实验室重放。

**产品能力**

把一次运行拆成可重复条件：

- 同一初始状态；
- 同一模型版本；
- 同一策略版本；
- 同一故障序列；
- 同一随机种子；
- 同一控制周期和截止时间；
- 同一九信号记录。

**客户价值**

将“偶发 bug”变成可重复实验，而不是靠再摔一次碰运气。

### 2.3 “危险场景不用拿真机试”

**客户问题**

以下测试在真机上很难做：

- 编码器突然冻结；
- 通信延迟突然增大；
- 单关节力矩衰减；
- 推理线程卡死；
- 策略输出完全错误；
- 控制周期连续 overrun；
- 负载或惯量突然改变。

真机测试成本高、风险大，还可能损坏客户样机。

**产品能力**

在 HIL/RT-SIL 环境中安全制造这些故障，验证：

- 策略如何退化；
- governor 是否接管；
- 回退是否稳定；
- 多久进入安全态；
- 是否留下完整证据。

**客户价值**

将高后果故障从“只敢想”变成“每天可以跑”。

### 2.4 “策略可以犯错，机器不能失控”

**客户问题**

学习型策略不可完全证明：

- OOD 状态无法穷举；
- 模型误差无法消除；
- 策略上线后可能输出离谱动作；
- 只靠策略自监控没有独立安全边界。

**产品能力**

平台内置独立 runtime assurance 路径：

- 包络监视；
- 速度、力矩、姿态和关节限制；
- 策略输出超时；
- overrun 连续检测；
- 确定性回退控制器；
- SAFE 状态和人工复位；
- 硬件驱动、FPGA 或看门狗作为最后防线。

**客户价值**

策略仍然可以迭代，但最坏结果被限制在可控范围内。产品卖点不是“保证策略成功”，而是“策略失败时系统仍可控”。

### 2.5 “模型不是摆设，差异有证书”

**客户问题**

仿真结果经常无法解释真机：

- 模型参数不准；
- 接触和摩擦过度简化；
- 执行器内部动态没建；
- 仿真能过，真机却失败；
- 不知道结果能信到什么程度。

**产品能力**

- 导入 MJCF/URDF/Isaac 模型；
- 用真机数据做系统辨识；
- 编译成实时降阶模型；
- 输出与高保真参考模型的误差；
- 标注有效频率范围、测试集和适用工作空间；
- 对比仿真与真机轨迹、周期、峰值和事件时间。

**客户价值**

客户不是得到一句“模型应该差不多”，而是得到：

- 模型在哪些条件下可信；
- 误差有多大；
- 超出范围后应如何降级。

### 2.6 “一天跑完一批退化场景”

**客户问题**

手工测试通常：

- 靠人记场景；
- 每次重新配置；
- 难以比较版本；
- 失败无法自动回归；
- 测试结果散落在日志和录像中。

**产品能力**

- 统一场景 DSL；
- 场景同时生成训练随机化配置和台架故障序列；
- 参数矩阵和多种子运行；
- 自动统计成功、失败、接管和 SAFE；
- 批量回归。

**客户价值**

测试从“工程师手工操作”变成“可调度的验证资产”。

### 2.7 “每次失败都有黑匣子”

**客户问题**

一次性故障经常只剩：

- 一段视频；
- 一段终端输出；
- 一句“刚才抖了一下”；
- 无法关联模型、策略、时序和硬件版本。

**产品能力**

统一记录：

- 时间戳；
- 角度；
- 角速度；
- 力矩；
- 策略目标；
- 推理延迟；
- 包络状态；
- governor 状态；
- 注入故障。

报告自动标记：

- 注入开始和结束；
- 首次越界；
- 回退接管；
- SAFE；
- 最大力矩；
- overrun 和推理超时。

**客户价值**

故障不再是“感觉”，而是可回放、可对比、可归档的工程证据。

### 2.8 “不要求客户改训练管线”

**客户问题**

机器人团队通常已经投入：

- MuJoCo/Isaac；
- PyTorch/JAX；
- PPO/SAC/模仿学习；
- ONNX/TorchScript；
- 自研训练框架。

客户不愿意为了测试平台重写训练和部署栈。

**产品能力**

平台只接管部署前验证：

- 导入现有模型和策略；
- 支持 ONNX/TorchScript；
- 保留客户训练管线；
- 通过 ROS 2/ros2_control 或 SDK 接入；
- 输出结果可回到客户现有调试流程。

**客户价值**

降低采用门槛，让平台成为验证基础设施，而不是另一套需要迁移的生态。

## 3. 机器人行业痛点与解决方案

| 痛点 | 现状 | 平台解决方案 |
|---|---|---|
| Sim2real 断层 | 仿真和真机之间缺少系统化验证环节 | RT-SIL、HIL、执行器在环和仿真/真机对比 |
| 真机测试昂贵 | 样机稀缺、场地受限、损坏成本高 | 虚拟 Plant、故障注入、提前回归 |
| 故障不可复现 | 依赖人工、时序和现场状态 | 固定模型、场景、种子、时基和九信号 |
| 危险场景不敢测 | 真机风险高 | 可控注入、独立安全通道、governor 兜底 |
| 失败归因困难 | 分不清模型、策略、时序、总线和执行器 | 分层信号、模型误差证书、事件时间线 |
| 测试资产难复用 | 场景靠脚本和口头传递 | 场景 DSL、版本化配置、自动回归 |
| 模型可信度不清 | “仿真里效果不错”无法量化 | 系统辨识、误差证书和适用范围 |
| RL 策略不可证 | 分布外行为无法穷举 | 不证明策略安全；证明监视器和回退路径 |
| 认证证据不足 | 日志、复现和追溯不成体系 | 统一信号字典、自动报告、测试追溯链 |

## 4. 总体方案设计

### 4.1 架构总览

```text
┌──────────────── Host / GPU / 非实时 ────────────────┐
│ 完整 MuJoCo / Isaac                                │
│ 训练、模型辨识、模型降阶、误差证书                   │
│ 场景 DSL、测试矩阵、回放、报告                       │
└──────────────────────┬─────────────────────────────┘
                       │ 模型、策略、场景、配置
┌──────────────────────▼──── 实时目标机 ───────────────┐
│                                                     │
│  RT CPU                                             │
│  实时降阶 Plant / 多关节动力学                       │
│  1kHz 控制 / PD / Governor / 安全仲裁                │
│  50–100Hz 策略推理 / timeout / latest-value buffer   │
│                                                     │
│  FPGA（按需）                                        │
│  EtherCAT DC / 编码器 / PWM / 硬件时间戳             │
│  电机电气模型 / 执行器仿真 / 故障注入 / 看门狗        │
│                                                     │
└──────────────────────┬─────────────────────────────┘
                       │ EtherCAT / RS485 / ADC / DAC
┌──────────────────────▼──── 被测对象 / 台架 ──────────┐
│ 真实控制器、真实关节、真实电机、真实传感器            │
│ 电机驱动保护、限流、急停                              │
└─────────────────────────────────────────────────────┘
```

### 4.2 各层的产品职责

#### Host / GPU

- 完整 MuJoCo/Isaac 高保真仿真；
- 训练和离线验证；
- 模型导入与系统辨识；
- 模型降阶与误差证书；
- 场景定义、报告生成和覆盖分析；
- 不参与硬实时闭环。

#### RT CPU

- 运行实时降阶 Plant；
- 1kHz 控制周期；
- 多关节刚体动力学；
- 推理调度和 timeout；
- governor 与回退控制；
- 测试调度和九信号记录；
- 全局逻辑和复杂故障模型。

#### FPGA

- 微秒级 I/O；
- EtherCAT DC 和编码器协议；
- PWM 与电机指令；
- 高频电机电气模型；
- 编码器/传感器仿真；
- 硬件故障注入；
- 安全看门狗和硬件保护。

FPGA 不承担通用 MuJoCo 物理引擎，也不替代 RT CPU 的多体动力学和控制逻辑。

### 4.3 核心软件模块

| 模块 | 功能 |
|---|---|
| 模型导入 | MJCF/URDF/Isaac 模型导入和规范化 |
| 模型编译 | 降阶、线性化、固定步长、可调度性检查 |
| 误差证书 | 高保真参考模型与实时模型误差统计 |
| 策略桥 | ONNX/TorchScript、ROS 2/ros2_control 接入 |
| 有界推理 | 超时检测、旧值保持、连续超时计数 |
| Governor | 包络监视、仲裁、回退和 SAFE |
| 场景 DSL | 训练随机化与台架故障注入共用定义 |
| 故障注入 | 延迟、丢帧、漂移、力矩衰减、硬件故障 |
| 实时 Plant | 固定步长、确定性多体或执行器模型 |
| Host 控制台 | 测试矩阵、实时曲线、回放和报告 |
| 覆盖度量 | 状态空间、接触状态、OOD 区域统计 |

### 4.4 三条必须坚守的架构原则

1. **控制周期内不做不可控计算**
   - NN 不进入 1kHz 拍；
   - 推理在独立线程或单元运行；
   - 主循环只读取最近有效输出。

2. **安全监控不依赖被污染的功能通道**
   - 故障注入只污染策略/PD 功能通道；
   - governor 使用原始编码器安全通道；
   - 最后一道防线在驱动器、FPGA 或硬件看门狗。

3. **仿真结果必须带适用范围**
   - 完整 MuJoCo 是参考，不是实时运行时全部；
   - 降阶模型要有误差和适用条件；
   - 不用“仿真通过了”替代真实证据。

## 5. 典型客户工作流

### 第一步：导入现有资产

- 导入 MJCF/URDF/Isaac 模型；
- 导入 ONNX/TorchScript 策略；
- 导入现有控制器接口；
- 选择真实总线或仿真总线。

### 第二步：建立可信模型

- 真机自由摆、阶跃或激励实验；
- 辨识质量、惯量、阻尼、摩擦和延迟；
- 生成实时模型；
- 与高保真 MuJoCo 比较；
- 输出误差证书和适用范围。

### 第三步：配置场景

客户描述：

> “延迟 5ms、10% 编码器丢帧、力矩衰减 30%，跑 30 秒，10 个种子。”

系统转换为：

- 训练侧随机化配置；
- 台架侧故障注入序列；
- 成功标准和报告模板。

### 第四步：运行真机前测试

- RT-SIL；
- 控制器 HIL；
- 单关节执行器 HIL；
- 可选 FPGA 电机/执行器仿真；
- 批量退化场景。

### 第五步：调试和归因

- 一键重放失败；
- 查看九信号时间线；
- 比较仿真和真机；
- 查看模型误差、时序和 governor 事件；
- 判断问题属于模型、策略、时序、总线还是执行器。

### 第六步：回归

- 修改模型或策略；
- 重跑原失败场景；
- 检查是否修复；
- 检查是否引入新增失败；
- 归档报告。

## 6. MVP 与产品路线

### 6.1 当前产品验证重点

当前 Task D 不是完整产品，而是产品能力的最小技术证明。

阶段 1：D-Lite MBD 最小垂直切片。

要证明：

- 仿真自由摆能解释真机趋势；
- 少量参数辨识能改善模型一致性；
- 同一模型参数能够生成有效制动控制；
- 同一 governor 能在仿真和真机自动接管；
- 测试可重复、可记录、可报告。

阶段 2：完整单摆 Demo。

要证明：

- 100Hz RL 策略和 1kHz 控制分层可行；
- ONNX 推理和 timeout 降级可行；
- 延迟、丢帧和力矩衰减可复现；
- governor 能拦截真实失效；
- A/B 和配重实验能形成证据链。

### 6.2 产品里程碑

| 阶段 | 产品能力 | 验证目标 |
|---|---|---|
| M0 | 接口、信号字典、时基和预算冻结 | 软件/FPGA/RTOS 可集成 |
| M1 | 单关节 HIL + governor + 故障注入 | RL 控制器在真实关节前可控验证 |
| M2 | 模型编译 + 误差证书 | MJCF/URDF 可快速生成可信实时模型 |
| M3 | 场景 DSL + 故障库 + 覆盖度量 | 批量退化场景自动执行和报告 |
| M4 | 感知 log-and-replay | 传感器退化可复现测试 |
| M5 | 认证追溯工具 | 测试报告映射到法规条款 |

### 6.3 首版不建议做的能力

- 完整 MuJoCo 搬 FPGA；
- 全自由度人形整机操作台架；
- 灵巧手接触 HIL；
- 实时渲染感知闭环；
- 宣称平台可证明策略绝对安全；
- 自建完整 ROS 2/Isaac 生态。

## 7. 竞争与差异化

| 现有方案 | 优势 | 缺口 | 本产品关系 |
|---|---|---|---|
| MuJoCo/Isaac | 高保真、生态好、训练方便 | 非硬实时，缺少故障和真机证据 | 上游模型和训练参考 |
| dSPACE | 汽车 HIL、确定性、认证体系成熟 | 昂贵，学习策略支持弱，机器人模型误差缺工具 | 方法论参照，不做汽车市场 |
| Speedgoat | Simulink 生态和快速控制原型 | 对 RL/ONNX/学习组件支持有限 | 可兼容模型导入 |
| TwinCAT/EtherCAT | 工业实时与总线成熟 | 缺少机器人模型、场景和策略验证层 | 底层总线与 I/O 生态 |
| 自研真机测试 | 真实、直接 | 昂贵、危险、不可复现、难归因 | 平台的最终验证补充对象 |

差异化不是“另一个物理引擎”，而是：

> **把学习组件的运行时保障、机器人模型误差、可复现故障注入和完整证据链接到一起。**

## 8. 产品成功指标

### 8.1 技术指标

- 1kHz 控制周期抖动和 overrun 达标；
- 推理 timeout 后系统按预期降级；
- governor 接管 `<5ms`、SAFE `<2s`；
- 仿真/真机自由摆周期误差 `≤10%`；
- 仿真/真机事件时间差可量化；
- 九信号完整率 100%；
- 报告一键生成。

### 8.2 产品指标

- 客户从导入模型到生成第一份报告的时间；
- 单次真机前测试可覆盖的场景数量；
- 失败场景复现成功率；
- 仿真/真机对比能定位问题的比例；
- 回归测试自动化率；
- 客户因提前发现问题而减少的真机占用和损坏；
- 同一失败重复运行时结果一致的比例。

## 9. 关键风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 模型误差过大 | 仿真结论不可信 | 误差证书、适用范围、真机对比 |
| 客户接口差异大 | 接入成本高 | 先支持 MuJoCo/ONNX/ROS 2；做适配层 |
| FPGA 被过度承诺为通用求解器 | 产品方向失焦 | 明确 FPGA 只做确定性 I/O 和执行器层 |
| 灵巧操作无法台架化 | 市场范围受限 | 首版聚焦 locomotion、关节和控制链 |
| 测试场景不足 | 客户价值不显著 | 标准故障库 + 场景 DSL + 自动生成 |
| 客户不愿意付费 | 商业化困难 | 先用明确问题和高频场景做试点 |
| 认证周期长 | 收入慢 | 先卖研发效率，再逐步建设认证能力 |

## 附：产品电梯陈述

> 机器人团队今天最大的问题不是缺少仿真，而是仿真和真机之间缺一层可复现验证：策略在 MuJoCo 里能跑，上真机后却可能因为延迟、丢帧、电机限制或推理超时而失效，而且失败往往无法复现。我们提供一个“真机前验证平台”，把客户现有模型和策略接入实时目标机，在真实 1kHz 时序、真实总线、真实执行器限制和可控故障下反复测试；策略跑飞时 governor 兜底，每次失败都有完整九信号时间线和报告。我们不替代 MuJoCo，也不承诺策略绝对安全，而是让团队在更早、更安全、更可复现的环境里，把该犯的错都犯完。
