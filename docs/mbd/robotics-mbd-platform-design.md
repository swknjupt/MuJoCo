## 1. 概念基础

### 1.1 硬实时与软实时

实时系统的本质不是"快"，而是 **deadline 可保证**：系统正确性不仅取决于计算结果，
还取决于结果**什么时候**产生。

| | 硬实时（Hard Real-Time） | 软实时（Soft Real-Time） |
|---|---|---|
| 错过 deadline 的后果 | 系统性失败，可能灾难性后果 | 服务质量下降，系统仍可用 |
| 正确性定义 | 迟到的结果 = 错误的结果 | 迟到的结果仍有价值，只是打折 |
| 统计要求 | 100%（按最坏情况 WCET 分析证明） | 大概率满足即可（如 99.9%） |
| 典型例子 | 安全气囊、电机电流环、PLC | 视频播放、语音通话、策略推理 |

中间态 **firm real-time**：偶尔错过没问题，但迟到结果直接丢弃（如 VoIP 丢包）。

三个关键理解：

1. **实时 ≠ 快**。平均 1ms 但偶尔抖到 50ms 的系统不是实时系统；稳定保证 10ms 的才是。
   实时关心的是最坏情况（WCET）与抖动（jitter）。
2. **硬实时是可证明的工程属性**，依赖 RTOS / PREEMPT_RT / Xenomai、确定性调度、
   受限的动态内存分配、可控中断延迟。
3. **越靠近"安全 + 物理执行器"，实时性要求越硬；越靠近人机交互，越软。**

### 1.2 RCP 与 HIL

同一个实时台架可以扮演两种角色：

| 角色 | 被测对象 | 对面是谁 | 场景 |
|---|---|---|---|
| **RCP**（快速控制原型） | 新控制器（跑在实时机上） | 真实执行器 / 仿真对象 | 新算法上车 / 上机前验证 |
| **HIL**（硬件在环） | 真实 ECU（被测件是真硬件） | 实时机仿真出的"虚拟物理世界" | 量产控制器验证，故障注入测试 |

### 1.3 商用 RT/HIL 平台现状

Speedgoat、dSPACE、NI CompactRIO 本质是同一物种：**把"硬实时 + 工业 I/O +
模型一键部署"打包卖的商业实时目标机**，服务于 MBD（基于模型的设计）流程。

| | Speedgoat | dSPACE | NI CompactRIO |
|---|---|---|---|
| 工具链 | Simulink Real-Time 官方搭档 | 自家生态 + Simulink 代码生成 | LabVIEW |
| 主场 | RCP（学术 / 航天 / 机器人原型） | **汽车 HIL 的事实标准** | 工业测试测量 |
| 强项 | 改算法迭代极快 | 故障注入、总线仿真、ISO 26262 配套 | FPGA 灵活、坚固嵌入式 |

dSPACE 的统治地位是被汽车行业结构"喂"出来的：标准化的被测件（ECU + CAN /
车载以太网）、强制法规（ISO 26262）、长周期、集中的主机厂-供应商体系。

### 1.4 经典 HIL 中的两个关键细节

**1kHz 闭环的含义**：每个 tick 必须在 1ms 内完成"读传感器 → 计算 → 写指令"整条链。
任何一拍超时（overrun）都意味着闭环不可信。与执行器的"统一"是两层含义：
频率上匹配执行器的指令周期（500Hz–1kHz 量级），时间上通过总线时钟同步
（如 EtherCAT Distributed Clocks，误差远小于 1µs）做到同拍。

**实时机上的 Plant 不是 MuJoCo/Isaac**：硬实时要求每一步耗时有界，而
MuJoCo/Isaac 的求解器耗时有抖动、跑在 GPU 上。因此经典 HIL 台架上仿真
"虚拟物理世界"的是**编译成确定性代码的简化动力学模型**。MuJoCo/Isaac
永远待在上游，以"导出的模型/策略"形态流入。

```
训练/离线验证:  MuJoCo / Isaac  (尽可能快, GPU, 非实时)   ← 上游
                        │  导出策略 (C/C++/ONNX) 与简化模型
                        ▼
实时台架:       控制器 + 简化 Plant 模型  (确定性, 1kHz)  ← dSPACE 方法论的地盘
                        │
                        ▼
                      真机
```

## 2. 背景：为什么机器人领域没有一个 dSPACE

### 2.1 dSPACE 的角色被"拆碎"了

| dSPACE 的功能 | 机器人领域的对应物 |
|---|---|
| 实时控制平台（RCP） | Speedgoat（实验室主流）、Beckhoff TwinCAT（工业 PC 控制 + EtherCAT） |
| 底层"执行器 ECU" | moteus / ODrive 等开源电机驱动、各家人形公司自研关节模组 |
| 总线 + 实时中间件 | EtherCAT 主站（IgH / SOEM）+ PREEMPT_RT Linux + ros2_control |
| HIL/SIL 验证 | 无人机界最成熟（PX4 HITL/SITL）；地面机器人基本缺位 |
| 开放实时接口 | Franka FCI 模式：厂商直接开放 1kHz EtherCAT 接口 |
| 认证/合规测试 | 基本空白（仅 ISO 10218 / ISO 13482 等安全标准，无配套工具链） |

### 2.2 创业公司为什么跳过 MBD

不是无视风险，而是理性计算后的选择：

| | MBD/dSPACE 哲学 | RL sim2real 哲学 |
|---|---|---|
| 对待模型误差 | 消灭它：精确建模 + 台架充分验证 | 包容它：domain randomization |
| 对待时序不确定 | 硬实时机器保证零抖动 | 训练时随机化延迟，让策略鲁棒 |
| 部署前验证 | 台架测试矩阵，覆盖故障场景 | 大规模并行仿真里"摔"几百万次 |

RL 用**训练时的分布覆盖**免疫未知，MBD 用**台架上的确定性**消灭未知。
创业公司跳过 MBD 的经济学原因：

- 工具链贵且为手调低维控制器设计，对 NN 策略部署支持是二等公民；
- 硬件便宜了（一台 Go2 比一套 Speedgoat 便宜），摔得起；
- 最需要硬实时的低层内环已有现成商品（关节模组自带 1kHz 电流环）；
- 迭代速度就是融资叙事，没有动力为"活不过两个月的策略版本"搭台架。

风险并没有消失，只是换了承担方式：不依赖策略的安全垫层（限位、限幅、
e-stop、摔倒恢复）、分阶段真机测试、把硬件损耗算进研发成本。
代价是**归因困难**（真机失败分不清模型误差还是时序 bug）和不可复现的时序问题。

### 2.3 回补的触发条件

跳过是融资阶段的最优解，不是终局。回到 MBD 式验证的触发条件：

1. **量产与法规认证**（ISO 10218 / ISO 13482 / 未来的人形机器人标准）——
   认证要求可复现的故障覆盖测试，台架是刚需；
2. **产品质量责任**——卖给工厂/家庭的机器人摔了要赔钱；
3. **规模效应反转**——出货量大了以后，台架的一次性投入被摊薄。

**结论：机器人领域不是没有对应产品，而是 dSPACE 的角色被三方分尸
（Speedgoat + TwinCAT + 开源 EtherCAT 栈），且行业集中度还没高到需要诞生
一个 dSPACE。等机器人进入汽车式的量产法规周期，这个空位会长出玩家——
这是本方案的机会窗口。**

## 3. 设计定位：确定性连续谱

### 3.1 一句话愿景

> 让学习到的策略在上真机之前，先在每一档"确定性递增、失败后果递减"的台阶上
> 被暴露。

机器人界缺的不是某台设备，而是"仿真 → 真机"之间整段确定性台阶：

```
MuJoCo/Isaac ──→ [空白]      ──→ [空白]    ──→ [空白]    ──→ 真机
  离线吞吐         RT-SIL          关节 HIL      感知 HIL       (创业公司直接跳到这)
  非实时           确定性简化模型    真关节×虚拟身体  回注/渲染       无任何中间验证
```

### 3.2 卖点重述

对创业公司的购买理由不是"你的策略验证通过了"（目前全行业做不到），
而是：

> **你的策略再离谱，机器也摔不了。**

即：runtime assurance（运行时保障）+ 可复现的退化场景测试。

## 4. 总体架构：三层

### 4.1 硬件层：实时目标机

参考 dSPACE/Speedgoat 的成熟结构，增加一块机器人特有的组件：

```
┌─────────────────────────────────────────────────────┐
│                  实时目标机                            │
│                                                     │
│  ┌───────────┐   ┌────────────┐   ┌──────────────┐  │
│  │ x86 RTOS  │   │    FPGA    │   │ 有界推理单元   │  │
│  │ 1–2kHz    │   │ µs 级子循环 │   │ timeboxed NN │  │
│  │ 整机闭环   │   │ EtherCAT DC│   │ 推理 + 回退   │  │
│  └───────────┘   └────────────┘   └──────────────┘  │
│                                                     │
│  工业 I/O: ADC/DAC / 编码器 / 故障注入矩阵             │
└─────────────────────────────────────────────────────┘
```

- **x86 RTOS 核心**：1–2kHz 整机闭环（读—算—写），抖动 µs 级，overrun 记录与报警。
- **FPGA**：EtherCAT DC 同步、电机指令生成、编码器解码、安全监控，
  时钟级确定性，绕开处理器调度。
- **有界推理单元（timeboxed inference）**：机器人特有需求。NN 推理耗时抖动，
  塞不进 1ms 拍。解法：推理窗口封顶（如 10ms），超时则沿用上一有效输出，
  同时由 governor（见 5.1）决定是否回退。这是 dSPACE 世界没有、
  机器人世界必须有的部件。

### 4.2 模型层：模型编译管线（真正的护城河）

```
MJCF / URDF / Isaac 场景
        │
        ▼
┌─────────────────────────────┐
│  模型编译管线                  │
│  系统辨识 + 模型降阶           │
│  → 确定性 RT 模型             │
│  → 误差证书                   │
└─────────────────────────────┘
        │
        ▼
部署到实时目标机（有界耗时、可调度性分析通过）
```

- **输入**：机器人团队已有的 MJCF / URDF / Isaac 场景，不要求重建模型。
- **输出**：确定性、实时可运行的简化模型；附**误差证书**——与高保真模型在
  测试集上的动力学偏差上界、有效频率范围、适用工作空间。
- **误差证书的意义**：汽车动力学模型本来就简单，dSPACE 不需要这个；
  机器人模型必须桥接 MuJoCo/Isaac 的高保真世界，"台架结果可信度"必须量化。
- **接口契约标准**（机器人的 "AUTOSAR"）：统一信号字典、频率、单位、
  时间戳语义。行业空白，谁定了谁就是标准。

### 4.3 工具链层：桥接两个世界，而不是取代谁

- **不与 RL 生态对抗**：ONNX / TorchScript 导入、ros2_control 桥、
  MuJoCo/Isaac 场景导入。训练管线原样保留，本平台只在"部署验证"处接管。
- **场景 DSL**：一份场景定义同时喂两端——训练时的 domain randomization
  与台架上的故障注入。杀手级特性：**"训练时你说策略见过 5ms 延迟，
  台架上真的注入 5ms 延迟验证"**——把"见过"从断言变成测试。
- **故障注入库（机器人特有）**：传感器漂移/掉帧、单关节失力矩、
  脚底打滑、通信延迟抖动、IMU 偏置、编码器丢拍。

## 5. 三个机器人特有的关键创新

### 5.1 策略 governor（运行时保障，Runtime Assurance）

整个产品最核心的一张牌。学习组件**不可证**，但安全包络监视器和
回退控制器**可证**：

```
策略输出 (50Hz, NN)
      │
      ▼
┌────────────────────────────┐
│  包络检查（可证，确定性）        │  力矩 / 速度 / 姿态 / 关节空间边界
│  通过 → 执行                  │
│  越界 → 回退控制器接管 + 安全停机 │
└────────────────────────────┘
      │
      ▼
低层控制 (1kHz, 硬实时) → 电机
```

这是航空界的 Simplex / runtime assurance 思路（ASTM F3269），大概率也是
未来人形机器人法规唯一能接受的路径：**"策略不可证，但监视器和回退控制器
可证"**——包络监视器与回退控制器本身是确定性、可验证、可通过认证的组件。

### 5.2 关节台架（Actuator-in-the-Loop）

机器人的"ECU HIL"对应物不是整机，而是**单关节**：

```
真实关节模组（含驱动器）
      ▲  1kHz+ 力矩/位置指令
      │
┌─────┴──────────────────────┐
│ 实时机：全身动力学仿真          │
│ 计算该关节在虚拟身体中承受的     │
│ 反作用负载（惯量、重力、接触）    │
└────────────────────────────┘
```

**真电机 × 虚拟身体**： locomotion 的大部分风险（负载突变、失步、热饱和、
打滑下的力矩需求）在这一档就能暴露，而不用拿整机去摔。物理结构与控制算法
都是全新的——汽车界没有对应物，因为汽车没有"全身动力学依赖单关节"的拓扑。

### 5.3 分布覆盖度量（替代需求覆盖）

传统验证问"**需求覆盖了吗**"；策略验证问"**状态分布覆盖了吗**"：

- 台架测试自动统计策略经历的状态空间覆盖度（关节空间、速度空间、
  接触状态、IMU 姿态流形）；
- 找出分布外的角落（OOD 区域），定向生成退化场景补测；
- 把学习社区的评测语言（分布偏移、OOD）翻译成验证社区的测试语言
  （覆盖、追溯、测试矩阵）。

这是方法论层面真正的创新：现有两种文化各自没有这套语言。

## 6. 最难啃的三个问题

| # | 问题 | 现实约束 | 务实策略 |
|---|---|---|---|
| 1 | **操作任务无法台架化** | 灵巧手操作"接触即物理"，虚拟物体给不出真实触觉 | 产品线重心放在 locomotion + 感知 + 安全层；操作验证保留"高保真仿真 + 真机" |
| 2 | **感知 HIL 的确定性** | 给真实相机喂渲染画面，渲染延时不确定 | 降级为 **log-and-replay**：真机采集数据流回注台架，测策略对传感器退化的反应，不追求实时渲染闭环 |
| 3 | **"覆盖了"不等于"安全"** | 分布覆盖是必要非充分条件 | 诚实卖点 = runtime assurance（governor 兜底），而非"证明策略安全"——后者全行业无解 |

## 7. MVP 路线

### 7.1 楔子产品

**先做"governor + 关节台架"**：

- 一台实时盒子（x86 RTOS + FPGA + EtherCAT）
- MJCF/URDF 导入 + 简化模型编译
- 包络监视器 / 回退控制器库（可证组件）
- 延迟 / 故障注入库
- Host 端测试报告（覆盖率、overrun 统计、场景矩阵）

对客户的一句话：

> "你的 RL 策略上真机之前，先在我们的台架上以 1kHz 接真关节跑；
> 策略跑飞我们兜底，一天跑完 200 个退化场景。"

需求真实、交付物具体、**不要求客户改训练管线**。

### 7.2 里程碑

| 阶段 | 交付物 | 验证目标 |
|---|---|---|
| M1 | governor 运行时 + 单关节台架 + 延迟注入 | 一个四足关节模组在台架上跑通 RL 策略 + 回退演示 |
| M2 | 模型编译管线 + 误差证书 v1 | MJCF → RT 模型自动化，误差上界可量化 |
| M3 | 场景 DSL + 故障注入库 + 覆盖度量 | 训练侧与台架侧共用同一套场景定义 |
| M4 | 感知回注档（log-and-replay） | 传感器退化场景的复现测试 |
| M5 | 认证工具链（ISO 10218 / 13482 映射） | 测试报告 → 法规条款的追溯链 |

## 8. 与现有生态的关系

| 生态 | 关系 |
|---|---|
| MuJoCo / Isaac | 上游训练环境，**不替代、只桥接**：导入场景、导出策略与简化模型 |
| ROS 2 / ros2_control | 部署中间件，提供桥接而非替换 |
| Simulink / Speedgoat | 传统 MBD 入口，兼容其模型导入 |
| Beckhoff TwinCAT / EtherCAT | 底层实时总线与工业控制组件供应商 |
| dSPACE | 方法论参照系，汽车市场不进入，只做机器人差异化 |

差异化定位一句话：**dSPACE 卖"确定性"，本平台卖"确定性 + 学习组件的
运行时保障"——前者是 20 世纪的问题，后者是当前机器人产业未解的问题。**

## 9. 术语表

| 术语 | 含义 |
|---|---|
| MBD | Model-Based Design，基于模型的设计：模型→自动代码生成→部署的工程流程 |
| WCET | Worst-Case Execution Time，最坏情况执行时间 |
| jitter | 抖动：周期性任务实际完成时刻相对理想时刻的偏差 |
| RCP | Rapid Control Prototyping，快速控制原型 |
| HIL | Hardware-in-the-Loop，硬件在环 |
| SIL | Software-in-the-Loop，软件在环 |
| overrun | 实时循环超时：某拍未在 deadline 内完成 |
| OOD | Out-of-Distribution，分布外：策略遇到训练分布之外的状态 |
| RoA / runtime assurance | 运行时保障：可证的安全监控 + 回退控制器兜底不可证的主系统 |
| Domain randomization | 域随机化：训练时随机化物理参数，使策略对失配鲁棒 |
| Governor | 本方案中的安全包络监视器 + 回退控制器的合称 |
| EtherCAT DC | EtherCAT 分布式时钟，µs 级总线时间同步机制 |
| Plant | 被控对象（的动力学模型） |
